    Отчет по лабораторной работе №3

    Упаковка FastAPI приложения в Docker, работа с источниками данных и очередями

    Цель работы

    Научиться упаковывать FastAPI приложение в Docker, интегрировать парсер данных с базой данных и вызывать парсер через API и очередь. Основной фокус — понять разницу между синхронным и асинхронным вызовом внешних сервисов.

    Подзадача 1: Упаковка в Docker

    Что было из прошлых работ

    Из ЛР1 у меня уже было готовое FastAPI приложение (тайм-менеджер) и база данных PostgreSQL. Из ЛР2 — функция парсинга HTML с получением заголовка страницы. Осталось всё это "завернуть" в контейнеры и заставить общаться друг с другом.

    Парсер как отдельный сервис

    Вместо того чтобы встраивать парсинг прямо в основное приложение, я вынесла его в отдельный микросервис. Для этого создала:

    • parser/parser_api.py — FastAPI приложение с единственным эндпоинтом /parse, который принимает URL и возвращает заголовок
    • parser/requirements.txt — зависимости для парсера (fastapi, uvicorn, requests, beautifulsoup4)
    • parser/Dockerfile — инструкция для сборки образа парсера

    Рефлексия: Отдельный контейнер для парсера кажется перебором для такой простой задачи, но это хорошая практика — сервисы должны быть слабо связаны. Если потом понадобится улучшить парсер или заменить его на другой, основной API останется без изменений.

    Dockerfile для основного приложения

    В корне проекта создала Dockerfile, который:

    • берёт образ Python 3.10-slim (лёгкий)
    • копирует requirements.txt и celery_requirements.txt (зачем он нужен — расскажу позже)
    • устанавливает зависимости
    • копирует весь код
    • запускает uvicorn

    Рефлексия: Я долго не могла понять, почему контейнер с парсером не видит файлы. Оказалось, в Dockerfile я указала COPY parser/requirements.txt, а нужно было COPY requirements.txt глупо но так забылось

    .dockerignore

    Чтобы в контейнер не копировались лишние файлы (виртуальное окружение, кэш, папка .git), я создала файл .dockerignore: pycache

    Это ускорило сборку образов и уменьшило их итоговый размер.

    Файл docker-compose.yml описывает 5 сервисов:

    • db — PostgreSQL, данные сохраняются в volume (чтобы не терялись при перезапуске)
    • redis — нужен для очередей (подзадача 3)
    • parser — сервис парсинга, собран из ./parser
    • app — основное FastAPI приложение, зависит от db, parser и redis
    • celery_worker — обработчик фоновых задач, тоже зависит от redis и parser

    Самое сложное было правильно настроить зависимости (depends_on) и понять, что контейнеры общаются друг с другом по имени сервиса (например, http://parser:8001), а не по localhost.

    Подзадача 2: Вызов парсера из FastAPI (синхронно)

    После того как парсер запустился в отдельном контейнере, нужно было добавить в основное приложение эндпоинт, который будет его вызывать.

    Что сделала

    В app/main.py добавила импорт httpx и новый эндпоинт:

    @app.post("/parse-url")
async def parse_url(url: str):
    async with httpx.AsyncClient() as client:
        response = await client.post("http://parser:8001/parse", params={"url": url})
    return response.json()

    Как это работает

    Клиент отправляет POST-запрос на /parse-url?url=...

    FastAPI обращается к контейнеру парсера по адресу parser:8001

    Парсер парсит страницу и возвращает заголовок

    FastAPI возвращает результат клиенту

    Тест

    curl -X POST "http://localhost:8000/parse-url?url=https://example.com"
json
{
  "url": "https://example.com",
  "title": "Example Domain",
  "status": "success"
}

    Рефлексия

    Синхронный подход работает, но есть проблема — пока парсер обрабатывает запрос (обычно 1-2 секунды), клиент висит в ожидании. Для одного запроса это нормально, но если пользователь отправит 100 URL, все будут ждать последовательно или перегрузится сервер.

    Подзадача 3: Асинхронный вызов через очередь (Celery + Redis)

    Что такое Celery и Redis

    Celery — библиотека для асинхронной обработки задач. Redis используется как брокер — он хранит очередь задач, которые ждут выполнения.

    Как это работает в моём проекте

    1. Клиент отправляет POST-запрос на /parse-url-async
    2. FastAPI не ждёт парсинга, а сразу создаёт задачу в Redis и возвращает клиенту task_id
    3. Celery worker видит новую задачу, выполняет парсинг (в фоне)
    4. Клиент позже может спросить результат по GET /task-result/{task_id}

    Что пришлось добавить

    1. celery_app.py — конфигурация Celery и задача parse_url_task. Задача делает то же самое, что и парсер, но теперь выполняется в фоне.

    2. celery_requirements.txt — отдельный файл с зависимостями для воркера (celery, redis, requests, beautifulsoup4). Основному приложению не нужны requests и beautifulsoup4, а воркеру они нужны, поэтому зависимости разделены.

    3. Два новых эндпоинта в app/main.py:

    @app.post("/parse-url-async")
def parse_url_async(url: str):
    task = celery_app.send_task("parse_url_task", args=[url])
    return {"task_id": task.id, "status": "queued"}

@app.get("/task-result/{task_id}")
def get_task_result(task_id: str):
    task = AsyncResult(task_id, app=celery_app)
    if task.ready():
        return {"task_id": task_id, "status": "completed", "result": task.result}
    else:
        return {"task_id": task_id, "status": "pending"}
    1. Сервис celery_worker в docker-compose.yml — он собирается из того же Dockerfile, но запускается с другой командой: celery -A celery_app worker --loglevel=info

    Тестирование асинхронного подхода

    # 1. Отправляем задачу (мгновенный ответ)
curl -X POST "http://localhost:8000/parse-url-async?url=https://example.com"
{"task_id": "abc-123", "status": "queued"}

# 2. Через секунду проверяем результат
curl "http://localhost:8000/task-result/abc-123"
{
  "task_id": "abc-123",
  "status": "completed",
  "result": {"url": "https://example.com", "title": "Example Domain", "status": "success"}
}

    Логи выполнения

    [INFO] Task parse_url_task succeeded in 1.283s: {'url': 'https://example.com', 'title': 'Example Domain', 'status': 'success'}

    Из логов видно, что воркер успевает обработать задачу за ~0.1-1.3 секунды в зависимости от размера страницы.

    Сравнение времени выполнения

    Подход Время ответа клиенту Время полной обработки Блокировка клиента
    Синхронный (/parse-url) ~1.3 сек ~1.3 сек ✅ да, ждёт
    Асинхронный (/parse-url-async) ~0.01 сек ~1.3 сек (в фоне) ❌ нет

    Рефлексия

    Разница очевидна. При синхронном подходе ответ приходит через 1-2 секунды — столько же, сколько парсится страница. При асинхронном — ответ приходит мгновенно (~0.01 сек), пользователь не ждёт.

    Особенно это важно, если нужно обработать много URL:

    • синхронно: 10 URL = 10-20 секунд ожидания
    • асинхронно: 10 URL ≈ всё ещё ~2 секунды, так как worker может обрабатывать несколько задач параллельно

    При росте нагрузки асинхронный подход легко масштабировать — достаточно добавить ещё один контейнер с celery_worker в docker-compose.yml.

    Итог выполнения

    Подзадача Что сделано Статус
    1 Dockerfile для app и parser, docker-compose.yml (5 сервисов: db, redis, parser, app, celery_worker) ✅
    2 Эндпоинт /parse-url для синхронного вызова парсера ✅
    3 Эндпоинты /parse-url-async и /task-result/{id}, Celery + Redis ✅

    Вывод по сравнению подходов

    Асинхронный подход через очередь оказался предпочтительнее для парсинга веб-страниц по нескольким причинам:

    1. Клиент не ждёт — ответ возвращается мгновенно (~0.01 сек), а не через 1-3 секунды.
    2. Параллельная обработка — несколько URL обрабатываются одновременно, а не последовательно.
    3. Масштабируемость — при росте нагрузки достаточно добавить ещё один контейнер celery_worker.

    Синхронный подход проще в реализации и подходит для единичных запросов или прототипирования, но плохо масштабируется и создаёт плохой пользовательский опыт из-за долгого ожидания.
