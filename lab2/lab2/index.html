    Задача 1. Различия между threading, multiprocessing и asyncio в Python

    Условие задачи

    Напишите три программы на Python, использующие подходы threading, multiprocessing и asyncio, для вычисления суммы всех чисел от 1 до N. Разбейте вычисления на несколько параллельных подзадач. Замерьте время выполнения каждой программы и сравните результаты.

    N = 100 000 000 (для получения репрезентативных результатов за разумное время).

    1. Общая функция calculate_sum()

    Для всех трёх подходов используется одна и та же функция, выполняющая вычисление суммы чисел на заданном диапазоне:

    def calculate_sum(start, end):
    total = 0
    for i in range(start, end + 1):
        total += i
    return total

    2. Многопоточный подход (threading)

    Файл: threading_sum.py

    Код программы

    import threading
import time
from sum_range import calculate_sum

TOTAL = 100_000_000
NUM_THREADS = 8

def worker(start, end, results, index):
    partial = calculate_sum(start, end)
    results[index] = partial
    print(f"Поток {index}: готов")

def main():
    chunk_size = TOTAL // NUM_THREADS
    results = [0] * NUM_THREADS
    threads = []

    start_time = time.perf_counter()

    for i in range(NUM_THREADS):
        start = i * chunk_size + 1
        end = (i + 1) * chunk_size if i < NUM_THREADS - 1 else TOTAL

        t = threading.Thread(
            target=worker,
            args=(start, end, results, i)
        )

        threads.append(t)
        t.start()

    for t in threads:
        t.join()

    total = sum(results)
    elapsed = time.perf_counter() - start_time

    print(f"Сумма: {total}")
    print(f"Время: {elapsed:.4f} сек")

if __name__ == "__main__":
    main()

    Как работает

    1. Общий диапазон [1, TOTAL] разбивается на 8 равных частей.
    2. Для каждой части создаётся отдельный поток.
    3. Потоки выполняются параллельно (или псевдопараллельно из-за GIL).
    4. Главный поток ожидает завершения всех потоков через join().
    5. Результаты суммируются.

    3. Многопроцессный подход (multiprocessing)

    Файл: multiprocessing_sum.py

    Код программы

    import multiprocessing
import time
from sum_range import calculate_sum

TOTAL = 100_000_000
NUM_PROCESSES = 8

def worker(start, end):
    return calculate_sum(start, end)

def main():
    chunk_size = TOTAL // NUM_PROCESSES
    tasks = []

    for i in range(NUM_PROCESSES):
        start = i * chunk_size + 1
        end = (i + 1) * chunk_size if i < NUM_PROCESSES - 1 else TOTAL
        tasks.append((start, end))

    start_time = time.perf_counter()

    with multiprocessing.Pool(processes=NUM_PROCESSES) as pool:
        results = pool.starmap(worker, tasks)

    total = sum(results)
    elapsed = time.perf_counter() - start_time

    print(f"Сумма: {total}")
    print(f"Время: {elapsed:.4f} сек")

if __name__ == "__main__":
    multiprocessing.freeze_support()
    main()

    Как работает

    1. Общий диапазон разбивается на 8 равных частей.
    2. Создаётся пул из 8 независимых процессов.
    3. Каждый процесс получает свою часть вычислений.
    4. Процессы выполняются на разных ядрах процессора.
    5. Результаты собираются через pool.starmap().

    4. Асинхронный подход (asyncio)

    Файл: asyncio_sum.py

    Код программы

    import asyncio
import time
from sum_range import calculate_sum

TOTAL = 100_000_000
NUM_TASKS = 8

async def worker(start, end):
    return calculate_sum(start, end)

async def main():
    chunk_size = TOTAL // NUM_TASKS
    tasks = []

    for i in range(NUM_TASKS):
        start = i * chunk_size + 1
        end = (i + 1) * chunk_size if i < NUM_TASKS - 1 else TOTAL

        tasks.append(
            asyncio.create_task(worker(start, end))
        )

    results = await asyncio.gather(*tasks)
    return sum(results)

if __name__ == "__main__":
    start_time = time.perf_counter()

    total = asyncio.run(main())

    elapsed = time.perf_counter() - start_time

    print(f"Сумма: {total}")
    print(f"Время: {elapsed:.4f} сек")

    Как работает

    1. Общий диапазон разбивается на 8 равных частей.
    2. Для каждой части создаётся корутина (задача).
    3. Задачи запускаются в цикле событий asyncio.
    4. Корутины выполняются в одном потоке, переключаясь только на операциях await.
    5. Поскольку функция calculate_sum() не содержит await, задачи фактически выполняются последовательно.

    6. Анализ результатов

    6.1. Почему multiprocessing самый быстрый?

    multiprocessing показал ускорение в 3.23 раза. Это объясняется тем, что:

    • Каждый процесс имеет собственный интерпретатор Python и собственный GIL.
    • Процессы выполняются на разных физических ядрах процессора.
    • Задача равномерно распределяется между доступными ядрами.

    6.2. Почему threading медленнее синхронного кода?

    threading оказался медленнее на 11 %. Причины:

    • GIL (Global Interpreter Lock) не позволяет потокам выполнять Python-код одновременно.
    • Потоки конкурируют за захват GIL, тратя время на переключение контекста.
    • Накладные расходы на создание и синхронизацию потоков не окупаются.

    6.3. Почему asyncio самый медленный?

    asyncio показал наихудший результат. Причины:

    • asyncio предназначен для I/O-bound задач, а не для вычислений.
    • Корутины выполняются последовательно, поскольку внутри calculate_sum() отсутствуют точки переключения (await).
    • Работа цикла событий добавляет дополнительные накладные расходы.

    7. Вывод

    В ходе выполнения лабораторной работы были получены следующие результаты:

    Вывод Подтверждение
    Multiprocessing — единственный подход, дающий реальное ускорение для CPU-bound задач ✅ Ускорение в 3.23 раза
    Threading не подходит для вычислений из-за GIL ❌ Медленнее синхронного кода
    Asyncio не предназначен для CPU-задач ❌ Самый медленный результат

    Итог

    Для вычислительных (CPU-bound) задач наиболее эффективным подходом является multiprocessing, поскольку он обеспечивает настоящий параллелизм за счёт использования нескольких процессов и ядер процессора.

    Подход threading не позволяет получить ускорение при выполнении вычислений из-за ограничения GIL, а asyncio предназначен главным образом для I/O-операций и не подходит для интенсивных вычислительных задач.

    Следовательно, для задач, связанных с большими объёмами вычислений, рекомендуется использовать multiprocessing, а threading и asyncio применять преимущественно для работы с сетью, файлами и базами данных.

    Задача 2. Параллельный парсинг веб-страниц с сохранением в базу данных

    Условие задачи

    Напишите три программы на Python, использующие подходы threading, multiprocessing и async, для параллельного парсинга веб-страниц с сохранением данных в базу данных из лабораторной работы №1.

    Выполнение задания

    Шаг 1. Подготовка списка URL-адресов

    Для парсинга были выбраны страницы книг с сайта Project Gutenberg — библиотеки бесплатных электронных книг. Было собрано около 100 URL-адресов формата https://www.gutenberg.org/ebooks/XXXX. Список URL сохраняется в файле urls.txt.

    Функция divide_into_chunks() (в файле parser_utils.py) разбивает общий список URL на равные части для распределения между потоками, процессами или асинхронными задачами.

    Шаг 2. Функция parse_and_save

    В файле parser_utils.py реализована функция parse_gutenberg_book(url), которая выполняет следующие действия:

    • Загружает HTML-страницу книги по указанному URL с помощью библиотеки requests
    • Парсит страницу с помощью BeautifulSoup
    • Извлекает название книги из тега <title> (очищая его от суффикса " by Author")
    • Извлекает имя автора из таблицы bibrec, которая присутствует на каждой странице Gutenberg
    • Извлекает числовой идентификатор книги из URL (последняя часть адреса)
    • Возвращает словарь с ключами: url, title, author, gutenberg_id

    Для асинхронной версии используется аналогичная функция parse_page_async(), работающая с aiohttp.

    Сохранение в базу данных выполняется через функцию save_book_as_task() в файле db.py. Она создаёт новую задачу в таблице tasks (из лабораторной работы №1) с параметрами: - title — "📖 Прочитать: {название книги}" - description — автор, ссылка и Gutenberg ID - priority — 3 (средний) - status — "pending" - project_id — ID проекта "Книги к прочтению" - user_id — ID текущего пользователя

    Шаг 3. Программа с использованием threading

    Файл: threading_parse.py

    В этой программе создаётся 8 потоков (класс threading.Thread). Каждому потоку передаётся свой чанк URL-адресов. Потоки запускаются одновременно, главный поток ожидает их завершения через метод join().

    При выполнении HTTP-запроса поток освобождает GIL, что позволяет другим потокам выполняться. Это даёт конкурентность в рамках одного процесса. После загрузки и парсинга каждая книга сохраняется в БД через вызов save_book_as_task().

    Шаг 4. Программа с использованием multiprocessing

    Файл: multiprocessing_parse.py

    В этой программе создаётся 8 независимых процессов (класс multiprocessing.Process). Каждый процесс получает свой чанк URL-адресов. Процессы запускаются одновременно, главный процесс ожидает их завершения через метод join().

    Каждый процесс имеет собственный интерпретатор Python и собственный GIL, что позволяет обойти ограничения GIL. Однако создание процессов требует больше ресурсов, чем создание потоков. Это особенно заметно при большом количестве лёгких операций (как в случае с сетевыми запросами).

    Шаг 5. Программа с использованием async/await и aiohttp

    Файл: async_parse.py

    В этой программе используется асинхронный подход. Все запросы выполняются в одном потоке через цикл событий asyncio. Для HTTP-запросов используется библиотека aiohttp, которая поддерживает неблокирующие операции.

    Создаётся 8 асинхронных задач (через asyncio.gather()). При ожидании ответа от сервера (оператор await) управление передаётся другой задаче, что позволяет эффективно использовать один поток для множества одновременных запросов. Сохранение в БД происходит после получения результата каждой задачи.

    Шаг 6. Запуск и замер времени

    Файл: runner.py

    Скрипт-оркестратор последовательно запускает все три подхода. Перед каждым запуском база данных очищается от предыдущих данных (функция clear_tasks()), чтобы результаты не накапливались. Время выполнения каждого подхода замеряется с помощью time.perf_counter() и выводится в консоль.

    Результаты выполнения

    Threading (8 потоков): время выполнения составило 27.72 секунды

    Multiprocessing (8 процессов): время выполнения составило 42.08 секунды

    Asyncio (8 задач): время выполнения составило 7.62 секунды

    Сводная таблица результатов

    Подход Количество воркеров Время (сек)
    Asyncio 8 задач 7.62
    Threading 8 потоков 27.72
    Multiprocessing 8 процессов 42.08

    Анализ результатов

    Почему Asyncio самый быстрый (7.62 сек)?

    Асинхронный подход не создаёт потоки или процессы, поэтому нет накладных расходов на их создание и переключение контекста. Все запросы отправляются почти одновременно, а цикл событий эффективно переключается между задачами во время ожидания ответа от сервера.

    Почему Threading медленнее (27.72 сек)?

    Потоки имеют накладные расходы на создание и переключение контекста. Хотя при I/O-операциях потоки освобождают GIL, переключение между потоками всё равно требует времени от операционной системы.

    Почему Multiprocessing самый медленный (42.08 сек)?

    Создание процессов требует значительно больше ресурсов, чем создание потоков. Каждый процесс инициализирует собственный интерпретатор Python. Для I/O-задач, где процессор не нагружен, эти накладные расходы не окупаются.

    Демонстрация сохранения в базу данных ЛР1

    После выполнения парсинга данные сохранились в таблицу tasks базы данных тайм-менеджера. Через Swagger-документацию (http://localhost:8000/docs) можно выполнить запрос GET /tasks/?project_id=3 и увидеть все созданные задачи в проекте «Книги к прочтению».

    Каждая задача содержит название книги, автора, ссылку на источник, приоритет и статус "pending" (ожидает выполнения).

    Вывод

    В ходе выполнения второй задачи лабораторной работы было установлено, что для I/O-задач (парсинг веб-страниц) наиболее эффективным подходом является asyncio (7.62 секунды). Он не создаёт лишних накладных расходов и эффективно управляет неблокирующими операциями ввода-вывода.

    Подход threading показал средний результат (27.72 секунды) — он допустим для I/O-задач, но уступает asyncio. Подход multiprocessing оказался самым медленным (42.08 секунды) и не рекомендуется для задач, связанных с сетевыми запросами.

    Данные успешно сохранились в базу данных лабораторной работы №1, что подтверждается через API тайм-менеджера.
